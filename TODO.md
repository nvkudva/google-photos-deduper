- [ ] Scale to 200,000 photos: target a full scan + review + delete pass without the tab becoming unusable. Measured baseline is 65 photos; the 98k-photo estimate (~55 min scan) is extrapolated from scroll geometry, not measured. Items below are the known blockers.
- [ ] Virtualise the results panel in src/overlay.js renderGroups: it renders up to 200 groups with one <img> per item, which is thousands of concurrent thumbnail loads at 200k scale. Paginate or windowed-render instead.
- [ ] Stop storing thumbnail URLs for review. src/scanner.js saves t.thumb to IndexedDB, but those URLs are signed and expire, so groups found early in a multi-hour scan show broken images by review time. Re-resolve from the live DOM at render time, or re-crop from a cached bitmap.
- [ ] Checkpoint scroll position during scan. src/scanner.js resumes with a full DB of known ids but still re-scrolls the whole grid (~28 min of dead scrolling at 98k), because nothing persists scrollTop. Save it to the meta store alongside lastScan and seek back on resume.
- [x] Add LSH banding to src/grouping.js so near-duplicate matching works across capture dates. Today only the exact-hash pass is global; the Hamming pass is bucketed by UTC day, so the same photo re-uploaded without EXIF (different capture date) is only caught if its 64-bit dHash matches byte-for-byte. Split each hash into four 16-bit bands, bucket on each band, compare within bands.
- [ ] Measure actual scan throughput at 5k and 20k photos before trusting the 200k projection. Log per-step timing (capture latency, tiles hashed, bytes) so the extrapolation can be replaced with real numbers.
- [ ] Check memory at 200k: the `known` Set in src/scanner.js holds every photo id (44 chars each, ~20MB of strings at 200k) for the whole run, and grouping loads every row via store.allItems() at once. Stream or page both if it bites.
- [ ] Reduce delete wall-clock: ~30 deletions per batch at ~7s a batch is ~40 min per 10,000. Test whether larger selections per "Move to bin" click hold up, and whether the 120ms inter-click delay in src/deleter.js can be cut.
- [ ] Handle the tab-visibility constraint over multi-hour runs. Google Photos stops rendering when the tab is hidden and captureVisibleTab needs it frontmost, so a 200k pass locks up a window for hours. Consider a dedicated window, or resumable chunks the user can run in sittings.
- [x] Guard against union-find chaining in src/grouping.js: members are merged transitively, so A~B and B~C puts A and C in one group even when A and C are 10 bits apart. The flat-crop fix removed the worst case, but a long chain of gradual near-matches can still over-merge. Consider capping group diameter, or splitting a group when its max pairwise distance exceeds ~2x the threshold.

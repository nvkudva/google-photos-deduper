- [ ] Scale to 200,000 photos: measured, not extrapolated. 29.95 photos/sec over a 2,025-photo run (111 scroll steps, 67.7s), so 200k is ~1.9 hours of scanning. Memory and IO are not blockers: rows are 309 bytes each (59MB at 200k), getAll() ~1s, the known-id Set 24MB. Grouping is ~800M comparisons, 4.8s, yielded so the worst main-thread block is 31ms. What is left below is delete wall-clock and running that long with the tab held in the foreground.
- [x] Virtualise the results panel. Turned out to be a correctness bug, not a performance one: rendering capped at 200 groups while every group was selected, so the delete button counted 149 photos that were not on screen. Results now page, and the selection covers exactly what has been rendered.
- [x] Stop storing thumbnail URLs for review. Measured instead of assumed: the URL is a stable per-photo token plus a size suffix, identical across sessions, so it does not expire the way the original note assumed. Results now prefer the live grid's URL when the photo is on screen, and a failed load shows an empty frame plus a count instead of a broken image. Revisit only if real expiry is ever observed.
- [ ] Checkpoint scroll position during scan. Less pressing than written: the range filter plus the bisection seek already let a stopped run continue by setting the range to end where it stopped, at a cost of ~12 probes rather than a full re-walk. Worth doing only as a convenience - store the oldest timestamp reached and offer to resume from it.
- [x] Add LSH banding to src/grouping.js so near-duplicate matching works across capture dates. Today only the exact-hash pass is global; the Hamming pass is bucketed by UTC day, so the same photo re-uploaded without EXIF (different capture date) is only caught if its 64-bit dHash matches byte-for-byte. Split each hash into four 16-bit bands, bucket on each band, compare within bands.
- [x] Measure actual scan throughput. Instrumented in src/scanner.js and stored on the lastScan meta row: 29.95 photos/sec, 18.2 photos per scroll step, split 58% screen capture and 42% waiting for thumbnails to paint. The two together account for 99.7% of wall clock, so any further speedup has to come out of one of them.
- [x] Check memory at 200k. Measured at 5,101 rows and scaled: 309 bytes per row (59MB at 200k), getAll() 25ms (~1s at 200k), the known-id Set 24MB against a 4GB heap limit. Not a bottleneck; no streaming needed.
- [ ] Reduce delete wall-clock: ~30 deletions per batch at ~7s a batch is ~40 min per 10,000. Test whether larger selections per "Move to bin" click hold up, and whether the 120ms inter-click delay in src/deleter.js can be cut.
- [ ] Handle the tab-visibility constraint over multi-hour runs. At the measured rate a 200k pass is ~1.9 hours with the tab frontmost, not the overnight job first assumed, but it still occupies a window for that long. Scoping by range is the current answer; a dedicated window would be better.
- [x] Guard against union-find chaining in src/grouping.js: members are merged transitively, so A~B and B~C puts A and C in one group even when A and C are 10 bits apart. The flat-crop fix removed the worst case, but a long chain of gradual near-matches can still over-merge. Consider capping group diameter, or splitting a group when its max pairwise distance exceeds ~2x the threshold.

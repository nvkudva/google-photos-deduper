- [ ] Scale to 200,000 photos: measured, not extrapolated. 29.95 photos/sec over a 2,025-photo run (111 scroll steps, 67.7s), so 200k is ~1.9 hours of scanning. Memory and IO are not blockers: rows are 309 bytes each (59MB at 200k), getAll() ~1s, the known-id Set 24MB. Grouping is ~800M comparisons, 4.8s, yielded so the worst main-thread block is 31ms. What is left below is delete wall-clock and running that long with the tab held in the foreground.
- [x] Virtualise the results panel. Turned out to be a correctness bug, not a performance one: rendering capped at 200 groups while every group was selected, so the delete button counted 149 photos that were not on screen. Results now page, and the selection covers exactly what has been rendered.
- [x] Stop storing thumbnail URLs for review. Measured instead of assumed: the URL is a stable per-photo token plus a size suffix, identical across sessions, so it does not expire the way the original note assumed. Results now prefer the live grid's URL when the photo is on screen, and a failed load shows an empty frame plus a count instead of a broken image. Revisit only if real expiry is ever observed.
- [ ] Checkpoint scroll position during scan. Less pressing than written: the range filter plus the bisection seek already let a stopped run continue by setting the range to end where it stopped, at a cost of ~12 probes rather than a full re-walk. Worth doing only as a convenience - store the oldest timestamp reached and offer to resume from it.
- [x] Add LSH banding to src/grouping.js so near-duplicate matching works across capture dates. Today only the exact-hash pass is global; the Hamming pass is bucketed by UTC day, so the same photo re-uploaded without EXIF (different capture date) is only caught if its 64-bit dHash matches byte-for-byte. Split each hash into four 16-bit bands, bucket on each band, compare within bands.
- [x] Measure actual scan throughput. Instrumented in src/scanner.js and stored on the lastScan meta row: 29.95 photos/sec, 18.2 photos per scroll step, split 58% screen capture and 42% waiting for thumbnails to paint. The two together account for 99.7% of wall clock, so any further speedup has to come out of one of them.
- [x] Check memory at 200k. Measured at 5,101 rows and scaled: 309 bytes per row (59MB at 200k), getAll() 25ms (~1s at 200k), the known-id Set 24MB against a 4GB heap limit. Not a bottleneck; no streaming needed.
- [x] Reduce delete wall-clock. Measured, and the cost is not where the note assumed. A deletion itself takes ~3s once the photo is on screen (2 deleted at 18s and 21s). The cost is finding targets: the deleter walks from the top at 1,100px per 500ms over a 2.5M-pixel scroller, so a full pass is ~19 minutes regardless of how many photos are being deleted - 166s of a real run covered 334k of 2.58M pixels and found 2 of 62. Fix by seeking to each target's capture date the way src/scanner.js already bisects, instead of scrolling past the whole library.
- [ ] Handle the tab-visibility constraint over multi-hour runs. At the measured rate a 200k pass is ~1.9 hours with the tab frontmost, not the overnight job first assumed, but it still occupies a window for that long. Scoping by range is the current answer; a dedicated window would be better.
- [x] Guard against union-find chaining in src/grouping.js: members are merged transitively, so A~B and B~C puts A and C in one group even when A and C are 10 bits apart. The flat-crop fix removed the worst case, but a long chain of gradual near-matches can still over-merge. Consider capping group diameter, or splitting a group when its max pairwise distance exceeds ~2x the threshold.
- [x] deleter: tiles under the 380px panel get a CDP click the panel swallows. Confirmed live: document.elementFromPoint at the safeRect centre of 7 of 38 clickable tiles returns DIV#gpdd-host. content.js never calls ui.setScanning(true) for a delete run, so the full panel is over the grid. Fix by reusing the scanbar for deletes, or by threading blockedRect into deleter.run the way hash.croppable already takes it. This, not the selection-toolbar reflow of 9a6ecf7, is the likely cause of "selection mismatch: clicked 2, 1 checked".
- [x] deleter.js run(): when picked is empty but checkedCount() > 0, the stale selection is never cleared and the next round aborts on the mismatch guard. Clear it before scrolling.
- [ ] selectors.js thumbUrl(): getComputedStyle(t).backgroundImage forces a style recalc for ~130 tiles 4x a second inside settle(). getAttribute('data-latest-bg') is free and is already used in overlay.js.
- [ ] store.js open(): dbp caches a rejected promise, so one IndexedDB open failure poisons the tab for the session. Null dbp on reject.
- [ ] background.js detach(): early-returns when attached lacks the tab, which after an MV3 worker restart leaves the debugger session and its banner up forever. The detach call is already try/catch-wrapped, so just always attempt it.
- [ ] scanner.js: await hash.hashRects() is unguarded, so a worker restart mid-scan aborts the whole run instead of pausing the way res.inactive does. Matters over a ~1.9h 200k scan.
- [ ] grouping.js keeper: sort by (a.ts || 0) makes a photo whose date failed to parse sort oldest and become the keeper, so the real original is the one binned. Prefer a parsed date over a null one.
- [ ] grouping.js: kind !== 'Video' tests a locale-formatted aria-label, so videos enter the pool on a non-English UI. Already leaks on English for Animation/Collage/Smile, which are not 'Video'.
- [ ] manifest.json: <all_urls> is dead (it was for the abandoned CORS-fetch plan) and hash.js hamming() is called nowhere. Drop both, and test whether captureVisibleTab still works without <all_urls> before committing.
- [ ] Not yet run destructively: the detail-view deleter has only been verified non-destructively (navigation, readiness, bin-button geometry). Test on one photo with a hard stop before trusting it with a full selection.
- [ ] selectors.js PHOTO_ID is /\/photo\/([^/?#]+)/, which does not stop at '&'. A stray anchor on the page has href '/photo/<id>&service=lh2&ec=GBRAHw', so readTile() returns an id with the query glued on. It is harmless today because such anchors have no thumbnail and never get hashed, but the id is wrong. Add '&' to the exclusion set.
